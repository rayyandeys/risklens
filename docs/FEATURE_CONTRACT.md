# BAF Base feature contract v1 — 27 September 2026

Source: Feedzai's official datasheet, question A7 (pages 2–3), A10–A11 (page 4).
https://github.com/feedzai/bank-account-fraud/blob/main/documents/datasheet.pdf
The PDF was downloaded and its text read during implementation. The short datasheet name
`device_distinct_emails` is mapped to the actual CSV name `device_distinct_emails_8w`.

## Intended scoring point and limitations

This is a benchmark classifier for a submitted application with captured session and internal
risk information. It is not a pre-application prediction system. Historical aggregate values
are assumed to represent information available then, as a benchmark assumption. The proprietary
original feature-generation code is unavailable, so point-in-time correctness cannot be proven.
Exclude `days_since_request` (elapsed time after application) and `device_fraud_count` (fraud
count without an explicit lookback/label-maturity guarantee) conservatively. Neither is declared
proven leakage. Any later inclusion must be a documented ablation, not a silent feature change.

`credit_risk_score` and `proposed_credit_limit` are assumed available at the stated scoring point;
plan ablations without them to expose reliance on an existing internal risk system.
Age is included for the academic benchmark, matching the available information. This is not a
fairness guarantee: retain it for subgroup evaluation and add a documented no-age ablation later.
No real applicant decisions or production lending suitability are claimed.

## Schema and cleaning

Require exactly the 32 columns from the user's audit; column order may differ. `fraud_bool` is
the target, `month` is partition metadata. There are 28 raw model inputs after four exclusions.

| Field(s) | Rule |
| --- | --- |
| prev_address_months_count, current_address_months_count, bank_months_count, session_length_in_minutes, device_distinct_emails_8w | Convert exactly -1 to missing |
| intended_balcon_amount | Convert every negative value to missing |
| credit_risk_score, velocity_6h | Preserve negatives: the datasheet allows them |
| payment_type, employment_status, housing_status, source, device_os | Training-fitted most-frequent imputation and one-hot encoding; unseen categories become all-zero encodings and are counted |
| All other numeric model inputs | Preserve values, impute missing with training median, standardize with training mean/variance |
| Six sentinel-bearing fields | Add explicit missing flags, including flags when no training row is missing |

Check numeric conversion and reject infinities; validate binary fields. This does not impose every
datasheet range as a hard rule, because generated numeric data may not exactly match rounded
descriptions. Constant training fields are logged. No learned preprocessing sees validation/test.

The first audit detected no literal nulls, but that does not mean no information is missing.
Its -1 counts were a preliminary screen. In particular, it did not count all negative transferred
amounts. The training summary records missing counts again after correct sentinel conversion.

## Duplicate and temporal checks

The new loader validates the CSV hash against the user's audit and rechecks month and development
target counts. It discards months 6–7 before feature diagnostics or fitting. It screens cleaned
training/validation feature rows using pandas 64-bit hashes, excluding target and month. Suspected
cross-split matches stop training pending exact review. Hash screening is not proof of entity
independence. There are no entity IDs; the datasheet describes independently generated instances.
Within-split duplicate counts are recorded for review, not silently deleted.

## Baseline specification

Two logistic regressions: unweighted and class_weight='balanced'. Both use L2 regularization,
C=1, lbfgs, maximum 1,000 iterations and tolerance 1e-4. No tuning/oversampling is done here.
Save convergence warnings and mark the run for review if convergence fails.

A constant training-prevalence predictor is a sanity baseline. Its tied top-k ranking uses a
seeded, label-free tie-break; exact random-ranking expectations are separately reported.
Budget k=floor(N*capacity); no review budget overspend. Predictions use original CSV row indices
as reproducible IDs. The test labels are never used for model or threshold selection.

Models, validation predictions, source hashes, dependencies, input hash and metric definitions
are saved per timestamped run. The latest summary is also written to reports/baseline_summary.json.
Only load joblib artifacts generated by this project from a trusted local run.
